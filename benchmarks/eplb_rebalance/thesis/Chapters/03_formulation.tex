\section{Migration instructions and flows}

Consider one MoE layer before and after a rebalance. Let $R$ be the set of EP
ranks and $E$ the set of logical experts. The old and new placement arrays
contain the expert identifier stored in every physical slot. Comparing the two
arrays determines which rank gains each expert. If a destination already owns
a copy, only a local rearrangement is needed; otherwise, one existing source
copy must supply the new replica.

A raw migration instruction is a tuple $(s,d,e)$ containing source rank $s$,
destination rank $d$, and logical expert $e$. Multiple experts may have the
same ordered rank pair. Since such transfers have identical endpoint
constraints, the scheduler coalesces them into a flow

\begin{equation}
  p=(s_p,d_p,E_p),
\end{equation}

where $E_p$ is the ordered set of expert identifiers assigned to the pair. Let
$w_p=|E_p|$ be the flow size in expert units. Coalescing reduces scheduler work
and prevents identical rank pairs from being artificially separated across
batches.

When an expert has several old replicas and several new destinations, the
source choice is also a scheduling decision in principle. The production
implementation preserves the existing vLLM assignment: destinations are
distributed as evenly as possible over source replicas in deterministic rank
order. Migration batching changes ordering, not placement semantics or replica
ownership.

\section{Problem inputs and output}

The optimization instance has five input groups: the coalesced migration flows
$P$ and their sizes $w_p$; the candidate batch set $B$; the routed-link set
$\mathcal{L}$ with capacities $C_e$; the fixed route fractions $f_{p,e}$; and
the foreground parameters $T_0$ and $\rho$. The optional diagnostic additionally
uses a fixed per-batch overhead $\delta$. These values describe what must move,
where it can travel, and how much network headroom remains for migration.

The required output is a batch assignment for every flow. Equivalently, the
solver returns the binary variables $x_{p,b}$ and $y_b$, from which the ordered
list of active batches is reconstructed. A valid output schedules every input
flow exactly once. The primary objective is the smallest worst-case modeled
inference time; among schedules with that value, the secondary objective is the
smallest number of active batches.

\section{Network model}

The offline model supports an explicit network graph and a compact two-tier
topology. In the latter, GPUs connect to server endpoints through local links;
server endpoints share a slower inter-server network. Let $\mathcal{L}$ be the
set of routed links and $C_e>0$ the normalized capacity of link $e\in\mathcal{L}$. Fixed
shortest-path ECMP determines $f_{p,e}$, the fraction of flow $p$ routed over
$e$. In the illustrative instance there is a single path for each flow, so
$f_{p,e}$ is binary.

The model measures flow size in expert units rather than bytes. It therefore
assumes equal expert payloads within the layer. This matches the evaluated
model architecture but would need extension for heterogeneous or quantized
experts. Following the bottleneck and residual-bandwidth view used in coflow
scheduling \cite{chowdhury2014varys}, it represents the bandwidth left by
foreground inference as $C_e(1-\rho)$, where $\rho\in[0,1)$ is the fraction of
link capacity occupied by inference. Varys estimates residual bandwidth from
measurements; the illustrative ILP instead uses one normalized $\rho$ for all
links. It is therefore a scenario parameter, not a deployment-independent
empirical constant.

\paragraph{Normalization and provenance.}
We adopt the 100~Gb/s intra-server and 50~Gb/s inter-server bandwidths reported
in Section V-A of DEMI \cite{zhang2025demi}. The example reduces the topology
to eight ranks; it is not a reproduction of DEMI's hardware deployment or our
Qwen serving cluster. Let $b_e$ denote physical bandwidth and $b_{\mathrm{ref}}$
be the reported inter-server bandwidth, 50~Gb/s, used as the normalization.
For equal expert payload size $S$, a
reference interval has duration $S/b_{\mathrm{ref}}$ when both use consistent
bit units. Capacity counts payloads transferable within that interval:

\begin{equation}
 C_e=\frac{b_e}{b_{\mathrm{ref}}}=
 \begin{cases}
 2 & \text{for a local link},\\
 1 & \text{for a network link}.
 \end{cases}
\end{equation}

Thus $C_e$ is not a bandwidth in Gb/s, and $L_{e,b}/C_e$ is dimensionless.
For a concrete illustration, DEMI reports a 7.64~MB expert; taking decimal MB
gives a 1.2224~ms reference interval. All model times below are expressed in
reference-interval units, not measured Qwen latencies. DEMI also defines
communication capacity as data transferable within a time slot (Section III-B).
The normalization fixes the example's offered load; scaling both capacities
without scaling the reference interval changes the scenario.

\paragraph{Multi-hop approximation.}
Each migration contributes load to every link on its route. Links are assumed
to support ideal streaming/pipelining, not whole-expert store-and-forward.
Network calculus shows that tandem rate--latency servers combine the minimum
rate with the sum of fixed latencies \cite[Theorem~1.4.6]{leboudec2001networkcalculus}.
We retain the bottleneck term and neglect per-hop propagation, startup,
packetization and staging delays. This is a simplifying assumption rather than
a verified characterization of every NIXL transport.

\section{Constrained integer linear program}

Let $P$ be the set of coalesced flows and $B=\{0,\ldots,|P|-1\}$ a safe upper
bound on candidate batches. The binary assignment variable is

\begin{equation}
x_{p,b}=\begin{cases}
1 & \text{if flow $p$ is assigned to batch $b$},\\
0 & \text{otherwise.}
\end{cases}
\end{equation}

Binary variable $y_b$ indicates whether batch $b$ is active, and
$T_{\mathrm{infer}}$ is a continuous variable for the worst modeled inference
time. Every flow is assigned exactly once:

\begin{equation}
  \sum_{b\in B}x_{p,b}=1 \qquad \forall p\in P.
  \label{eq:flow-once}
\end{equation}

Assignments activate their batch, and symmetry is reduced by requiring active
batches to form a prefix:

\begin{align}
  x_{p,b} &\leq y_b,\\
  y_b &\geq y_{b+1}.
\end{align}

The migration load on routed link $e$ in batch $b$ is

\begin{equation}
  L_{e,b}=\sum_{p\in P}w_p f_{p,e}x_{p,b}.
  \label{eq:link-load}
\end{equation}

Let $T_0$ be inference time without migration. The model assumes slowdown is
linear in migration load relative to normalized residual link capacity:

\begin{equation}
  T_{\mathrm{infer}} \geq
  T_0\left(1+\frac{L_{e,b}}{C_e(1-\rho)}\right)
  \qquad \forall e\in\mathcal{L},\;\forall b\in B.
  \label{eq:slowdown}
\end{equation}

The maximum-over-links structure follows the standard bottleneck observation
that a collection of parallel network flows is limited by its most heavily
loaded endpoint or link \cite{chowdhury2014varys}. Varys supports this bottleneck
abstraction, not the particular affine inference-slowdown law in
\cref{eq:slowdown}. That law is an explicit modeling assumption: it is neither
a calibrated latency predictor nor a proven upper bound on actual inference
latency. DEMI provides a related optimization of expert migration and token
traffic under shared capacity, but targets training and uses a different
time-indexed formulation \cite{zhang2025demi}. The primary optimization is

\begin{equation}
  T_{\mathrm{infer}}^*=\min T_{\mathrm{infer}}.
  \label{eq:primary-objective}
\end{equation}

Under this model, the first solve minimizes the maximum normalized link load
over all link--batch pairs. After obtaining $T_{\mathrm{infer}}^*$, the solver
runs a second optimization:

\begin{equation}
  B^*=\min\sum_{b\in B}y_b
  \quad\text{subject to}\quad
  T_{\mathrm{infer}}\leq T_{\mathrm{infer}}^*+\epsilon.
  \label{eq:secondary-objective}
\end{equation}

Here, $\epsilon$ is only a numerical tolerance. The second stage removes
unnecessary batches but cannot exchange a meaningful increase in inference
time for fewer batches. This lexicographic formulation avoids an arbitrary
weighted sum between foreground latency and batch overhead. The implementation
therefore performs two actual mixed-integer solves through SciPy's interface
to HiGHS \cite{scipy2020,huangfu2018highs}.

\section{Migration-time diagnostic}

The ILP deliberately optimizes modeled inference time, not migration time. To
make the trade-off visible, it reports a diagnostic. The duration of batch $b$
is approximated by its bottleneck-link service time:

\begin{equation}
  T_b=\max_{e\in\mathcal{L}}\frac{L_{e,b}}{C_e}.
\end{equation}

Given a per-batch launch or synchronization overhead $\delta$, total migration
time is estimated as

\begin{equation}
  T_{\mathrm{migration}}=\sum_b T_b+\delta\sum_b y_b.
  \label{eq:migration-time}
\end{equation}

Splitting one busy batch into several lighter batches can reduce the maximum in
\cref{eq:slowdown} while increasing the sum in \cref{eq:migration-time}. This
is not a contradiction. The two quantities answer different questions: the
first represents foreground interference; the second represents how long the
background reconfiguration remains unfinished.

\section{Illustrative hotspot instance}

The example contains eight GPU ranks, two GPUs per server, local-link capacity
2, network-link capacity 1, and $\rho=0.6$, leaving 40\% normalized link
headroom for migration. The capacities derive from the cited 100:50~Gb/s
bandwidths; the 60\% foreground share is an assumed illustrative scenario,
not a value measured in DEMI or in our experimental cluster. There is no
workload-independent inference bandwidth fraction. We retain $T_0=1$ and
$\delta=0.05$ as explicitly assumed normalized values. Eight migrations create
a shared-network hotspot. Because the same
$\rho$ multiplies every candidate link--batch pair, changing it uniformly
rescales the reported value of $T_{\mathrm{infer}}$ but does not change which
batch assignment minimizes the objective. A production predictor should
replace it with per-link residual bandwidth measured at runtime.

We repeat the two-stage solve at $\rho\in\{0,0.3,0.6,0.9\}$;
\cref{tab:rho-sensitivity} reports the results. Every solve selects three
batches and reduces the peak normalized link load from 3.00 to 1.00. This
checks the expected uniform rescaling; it does not validate the affine model
or heterogeneous traffic. The main example uses $\rho=0.6$ throughout.

rank-disjoint rule; that rule is not imposed on this ILP.

\section{Why the ILP is not used online}

The optimizer is intentionally separated from the serving path. It is not an
``optimal implementation'' of EPLB: it is an exact offline reference for one
restricted mathematical formulation. First, an
online solver would add SciPy/HiGHS dependencies and variable solve latency to
a periodic control operation. Second, the latency model in
\cref{eq:slowdown} is an abstraction. Real interference depends on transport
protocols, queueing, CPU progress, message sizes, and simultaneous inference
collectives. An exact optimum of an approximate model is not necessarily a
better production choice than a conservative rule.

Third, all ranks already possess the placement maps needed to construct the
same deterministic schedule. A lightweight local algorithm avoids a new
coordination service. The ILP remains valuable for explaining the objective,
checking small instances, and demonstrating the value of contention-aware
batching. The next chapter describes the conservative rule used by the
deployed scheduler.
